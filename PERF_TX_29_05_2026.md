## 1. Bugs P0 confirmes ( a corriger en priorite )

### P0-1 : `WorkflowLogRetentionTask` echoue chaque tick

**Fichier** : `backend/src/main/java/fr/inra/oresing/workflow/cascade/history/WorkflowLogRepository.java:458` ( pre-fix )

**Symptome observe** : 136 erreurs HTTP 4xx/5xx remontees pendant la
session , dont la trace systematique :

```
org.springframework.dao.DataIntegrityViolationException: PreparedStatementCallback;
SQL [SELECT oa_audit.delete_workflow_logs_older_than(?::int)];
A result was returned when none was expected.
```

**Cause racine** : la fonction PostgreSQL `delete_workflow_logs_older_than`
retourne un `int` ( le nombre de lignes purgees ) , donc l'instruction
SQL renvoie une row . Le code utilisait `jdbcTemplate.update(SQL, days)`
qui invoque `executeUpdate()` cote driver - le driver Postgres jette
parce qu'il y a un result set non consomme .

**Impact** :
- Backend log ERROR chaque minute ( scheduler `WorkflowLogRetentionTask` )
- Aucune purge de l'historique reellement effectuee -> table
  `oa_audit.workflow_log` grossit indefiniment
- Bloat index + degradation des queries d'historique au fil des mois
- Pollution Grafana ( faux signal d'erreur backend )

**Patch** : utiliser `queryForObject(SQL, Integer.class, days)` .
**Status** : applique dans la session ( commit en attente ) .

### P0-2 : Mode CACHED_ROTATION - `processed_data` Large Object orpheline

**Fichier** : `backend/src/main/java/fr/inra/oresing/persistence/BinaryFileRepository.java` ( voir `storeProcessedData` + V13 migration )

**Hypothese** : lors d'un republish CACHED_ROTATION qui reutilise
`processed_data` sans relancer DataImporter , si la chaine
clear-old + assign-new n'est pas dans la meme transaction , l'ancien
OID Large Object peut rester non reference + non delete -> bloat
`pg_largeobject_metadata` .

**Verification recommandee** :
```sql
-- Comparer le nombre d'OIDs dans pg_largeobject_metadata
-- vs le nombre de processed_data non-null dans binaryfile
SELECT COUNT(*) FROM pg_largeobject_metadata;
SELECT COUNT(*) FROM ticket_507_1.binaryfile WHERE processed_data IS NOT NULL;
-- Si l'ecart est > 0 , il y a fuite d'OIDs
```

**Mitigation** : ajouter un VACUUM LO scheduled , OU encapsuler
`storeProcessedData` dans un `@Transactional` qui DELETE l'OID
precedent via `lo_unlink` avant d'assigner le nouveau .

**STATUS ( verifie 30-05-2026 )** : DEJA RESOLU - et la migration LO
( #244 ) est DEJA active en local ( `binaryfile.processed_data` est de
type `oid` dans ticket_507 ET ticket_507_1 , pas bytea ) . Le `lo_unlink`
atomique recommande est en place , plus complet que la reco :
- `BinaryFileRepository.persistTempFileToLargeObject` : tx unique
  `REQUIRES_NEW` = unlink ancien oid -> `createLO` -> stream -> UPDATE
  `processed_data = newOid` . Echec partiel -> rollback complet ( au pire
  un LO orphelin reclame par vacuumlo / le sweeper ) .
- `BinaryFileRepository.clearProcessedData` : `lo_unlink` avant
  `SET processed_data = NULL` , `REQUIRES_NEW` , idempotent .
- `PublishFastPathDirectExecutor` : unlink du cache LO dans la meme tx
  que le republish FAST .
- `LargeObjectOrphanSweeper` ( `@Scheduled` cron `0 0 4 * * *` , toggle
  `app.large-object.orphan-sweep-enabled` ) : `lo_unlink WHERE loid NOT
  IN ( oids references )` = exactement le controle nightly de l'annexe 8.3 .
- Verifie live : `pg_largeobject_metadata` = 0 LO , 0 reference , **0 orphelin** .
=> aucun changement de code requis .

## 2. Risques d'incoherence ( P0/P1 )

### P0-4 : DELETE_FILE - non atomique entre `DELETE rows` + `DELETE binaryfile`

**Fichier** : `backend/src/main/java/fr/inra/oresing/rest/usecases/storage/versioning/PublishLifecyclePhase2Handler.java` , methode `doDeleteFile`

**Refacto recent** ( SLA cancel 5s ) : la methode a ete splittee en
deux phases visibles ( DELETE_ROWS + DELETE_FILE_ROW ) , chacune en
transaction propre via `PhaseScope` .

**Risque** : si Phase 2 ( DELETE_FILE_ROW ) echoue , Phase 1 est
committee = on a perdu les rows mais la binaryfile metadata reste -> incoherence
dans l'UI ( le fichier apparait dans l'historique mais sans donnees ) .

**Etat reel du code ( verifie session 29 mai )** :
- `DELETE_ROWS` = `DataRepository.removeByFileIdChunked` : suppression par
  **paquets de 10 000 lignes auto-commites** ( pre-delete `reference_reference`
  puis `referencevalue` ) , annulable entre chunks , WAL borne par chunk .
- `DELETE_FILE_ROW` = `removeFile` dans une tx `REQUIRES_NEW` ( atomique , 1 ligne ) .
- `PhaseScope` ne gere AUCUNE transaction : il ne publie que le nom de phase
  pour l'UI . Donc les 2 phases sont deja dans des tx independantes .

**Mode d'echec** : `DELETE_ROWS` committe ( lignes supprimees ) puis
`DELETE_FILE_ROW` echoue -> binaryfile orpheline ( apparait dans
l'historique mais sans donnees ) . Recuperable EN AVANT : relancer le
delete d'1 ligne est idempotent ; on ne veut PAS de rollback ( on voulait
supprimer de toute facon ) .

**Mitigation - decision ( B auto-reparation , pas C )** :
- Option A ( meme transaction ) : non - sur des dizaines de M de lignes ,
  verrous + WAL monolithiques , perte du cancel 5s .
- Option C ( SAVEPOINT ) : **rejetee pour le passage a l'echelle** .
  SAVEPOINT n'existe QUE dans une seule transaction -> force lignes +
  binaryfile dans une tx geante = exactement ce que le decoupage chunke
  evite . Coherent mais regression de perf majeure ( verrous tenus sur
  10M+ lignes , blocage lectures concurrentes , risque lock_timeout /
  deadlock ) . NB : un SAVEPOINT par batch est deja utilise *a l'interieur*
  de `StagingFinalizeSql` pour le rollback granulaire d'un batch UPSERT -
  c'est le bon usage ( petit perimetre ) , pas pour englober tout le DELETE .
- **Option B ( recommandee ) : compensation AUTO-REPARANTE** . Reutiliser
  le `CompensationLogService` existant ( saga + sweeper + handlers ) :
  `record()` d'une intention "finir DELETE_FILE_ROW" avant la Phase 3 ,
  `confirm()` au succes ; a l'echec le sweeper rejoue automatiquement le
  delete d'1 ligne -> fenetre d'incoherence bornee + auto-resolue , zero
  intervention admin . DRY ( infra deja presente ) , SOLID , scalable
  ( garde le decoupage chunke ) . Pas besoin d'un statut
  `PARTIAL_DELETE_FAILED` ni d'un endpoint admin manuel .

**Verdict** : **B ( auto-reparation ) > C** sur perf-a-l'echelle ET
coherence . Effort ~2 h ( handler `CompensationHandler` "DELETE_FILE_ROW"
+ record/confirm dans `doDeleteFile` + 1 test ) .

### P0-5 : PUBLISH staging -> final - race avec crash backend

**Fichier** : `backend/src/main/java/fr/inra/oresing/rest/usecases/storage/versioning/PublishLifecyclePhase2Handler.java` , methode `commitPublishVisibility`

**Scenario observe** :
1. Backend ouvre transaction , INSERT 1M rows dans `staging` UNLOGGED
2. Backend swap staging -> final via `INSERT INTO final SELECT FROM staging`
3. Backend crash entre commit COPY + commit visible_flag
4. Au redemarrage : final a deja les rows ( COPY committe ) , mais `binaryfile.published=false`

**Etat de la base** : incoherent . Les rows existent mais ne sont
pas visibles via l'API ( filtree par `published=true` ) .

**Fix existant** ( CONFIRME par lecture session ) : la transaction
finale englobe le swap + le `UPDATE binaryfile SET published=true`
+ le `recordEnd` workflow_log dans **une seule** tx ( P0-2 + P0-6 du
audit precedent ) . Donc theoriquement atomique .

**Risque residuel** : SHARED_UNLOGGED tables n'ont pas de WAL .
Si Postgres crash AVANT que le swap se finisse , la table staging
peut etre tronquee a redemarrage -> Phase 2 redemarrage doit
detecter staging vide + retraiter ( idempotence verifiee mais non
testee live ) .

**Recommandation** : ajouter un test de chaos engineering ( `pg_terminate_backend`
pendant le swap ) pour confirmer la recovery .

**STATUS ( analyse confirmee 29-05-2026 )** : invariant atomique verifie
en code . `commitVisibleFlagAndSynthesis` ( `PublishLifecyclePhase2Handler` )
s'execute dans UNE tx `TransactionTemplate` ( REQUIRES_NEW ) englobant
swap + toggle `binaryfile.published` + synthese ; si elle rollback , le
flag n'est PAS togglee -> etat coherent ( workflow_log=CANCELLED +
`published` inchange , aucune divergence ) . Au redemarrage JVM , le
`WorkflowZombieSweeper` ( cleanupOnBoot=true ) passe tout IN_PROGRESS
orphelin a CANCELLED , et le staging UNLOGGED orphelin est nettoye par
le sweeper TTL . Comme la tx de swap n'a pas committe , la table finale
n'a pas non plus les rows -> rien de demi-applique .

**Procedure de chaos test live ( a executer manuellement )** :
1. Lancer un PUBLISH sur un gros fichier ( staging SHARED_UNLOGGED ) .
2. Pendant la phase finalize , recuperer le backend pid via
   `BackendPidRegistry` ( expose par correlationId ) ou
   `SELECT pid , query FROM pg_stat_activity WHERE application_name='openadom-backend' AND query ILIKE '%referencevalue%';`
3. `SELECT pg_terminate_backend(<pid>);` pour simuler le crash mid-swap .
4. Verifier : la tx avorte ( aucune row visible , `published` inchange ) ,
   le workflow passe CANCELLED ( sweeper ) , aucun orphelin en table finale .
5. Re-declencher le PUBLISH -> succes idempotent ( staging re-rempli ) .
=> reste a derouler en live ( necessite un import reel + redeploy backend ) ;
le code garantit deja l'atomicite , le test ne fait que la confirmer .

### P1-1 : `WorkflowZombieSweeper` - marquage en double possible

**Fichier** : `backend/src/main/java/fr/inra/oresing/workflow/cascade/history/WorkflowZombieSweeper.java`

**Mecanisme** : scheduler appelle `mark_zombie_workflows(threshold_min)`
toutes les minutes . Marque IN_PROGRESS sans heartbeat depuis N min
comme ZOMBIE .

**Race** : 2 instances backend ( prod replicee ) -> 2 schedulers
concurrent -> double marquage de la meme ligne . La fonction SQL
utilise `UPDATE WHERE status=IN_PROGRESS AND last_heartbeat < threshold`
qui est protege par MVCC ( un UPDATE consume la row ) , donc OK en
theorie .

**Verification recommandee** : ajouter `FOR UPDATE SKIP LOCKED`
pour eviter contention au pire .

**Status ( verifie 29 mai )** : **DEJA EN PLACE** . `V4__oa_audit_complete.sql`
( bloc 6 , ~L201-233 ) definit `mark_zombie_workflows` avec un
`SELECT ... WHERE status='IN_PROGRESS' ... FOR UPDATE SKIP LOCKED` ( tache
#264 ) . Aucune action requise .

### P1-2 : `binaryfile.params->published` source de verite divergente

**Fichier** : `BinaryFilePublicationState` endpoint + frontend
DataVersioningView

**Pattern actuel** : 2 sources potentielles
- `binaryfile.params->>'published'` ( jsonb , verite committee )
- `workflow_log.status` ( IN_PROGRESS / DONE / CANCELLED )

**Risque** ( deja identifie + commentaire en code ) : cancel-divergence
- workflow_log.status=CANCELLED mais binaryfile.published=true ( commit

**Mitigation existante** : un endpoint dedie `/file/{id}/publication-state`

### P1-3 : DataImporter naturalkey collision intra-import

**Fichier** : DataImporter + V11 idx fonctionnel `binaryfile.params`

**Scenario** : 2 lignes du CSV en cours d'import partagent la meme
naturalkey ( bug user ) . Comportement actuel : la 2eme ligne UPDATE
la 1ere dans `staging` , puis le swap final voit qu'une seule row .
**Probleme** : aucune erreur de validation , user pense que les 2
lignes ont ete inserees .

**Mitigation recommandee** : pre-scan `NaturalKeyPreScanService` doit
detecter les doublons intra-import + reporter au user avant
finalisation ( la tache #287 est ouverte sur ce sujet ) .

**Meilleure proposition ( plus DRY + scalable )** : ne PAS refaire une
passe separee sur le fichier . Les donnees sont DEJA dans le staging apres
le COPY ; detecter les doublons par un simple agregat SQL juste avant
l'UPSERT , dans `StagingFinalizeSql` :

```sql
SELECT (data->>'<naturalKeyExpr>') AS nk, count(*) AS n
FROM <staging>
GROUP BY 1 HAVING count(*) > 1
LIMIT <maxReport>;
```

- 1 seul scan de staging ( deja en RAM/cache , UNLOGGED ) au lieu d'une
  passe fichier supplementaire .
- **Autoritatif** : c'est exactement la cle que l'UPSERT `ON CONFLICT`
  va fusionner silencieusement ; on la capture AVANT au lieu de la perdre .
- Si `n > 1` -> remonter en erreur de validation ( meme canal que
  `InvalidDatasetContentException` ) ou en warning configurable
  ( `fail-on-intra-duplicate` ) , avec les lignes concernees .
- Generique ( marche pour tout datatype , recursif ou non ) , testable
  ( fixture staging ) , aucun cout sur le chemin nominal sans doublon .

=> remplacer / completer #287 par cette detection cote staging plutot
qu'une passe fichier .

**STATUS ( implemente 29-05-2026 )** : fait cote staging , generique +
testable , 0 passe fichier , 0 heap JVM .
- Nouvelle classe `IntraImportDuplicateDetector` ( read-only ) appelee dans
  `StagingFinalizeSql.runFinalize` APRES le COPY/ANALYZE et AVANT toute
  mutation ( refref rebuild + UPSERT ) , donc un echec ne laisse aucun
  effet de bord .
- Cle de groupement = les 4 colonnes de la contrainte
  `hierarchicalKey_uniqueness` ( `application , referenceType ,
  hierarchicalKey , patternColumnName` ) extraites de `data` JSONB
  ( cles minuscules ) = **exactement** les champs que l'UPSERT `ON CONFLICT`
  resout -> autoritatif par construction , aucune re-derivation de cle .
- 1 scan agregat ( count groupes + lignes excedentaires ) ; la requete
  d'echantillon ( `LIMIT 20` ) n'est emise que si des doublons existent .
- Politique configurable `cascade.import.intra-duplicate-policy` (
  env `CASCADE_IMPORT_INTRA_DUPLICATE_POLICY` , editable a chaud oa-live ) :
  - `OFF` : aucun scan , comportement historique strict ( 0 overhead ) .
  - `WARN` ( **defaut** ) : scan + log detaille , puis l'UPSERT se deroule
    comme avant -> **meme resultat final garanti** ( pas de regression ;
    le defaut ne durcit rien , il ne fait que tracer ) .
  - `FAIL` : leve `IntraImportDuplicateException` avant mutation ( remplace
    le `SQLSTATE 21000` opaque intra-batch et le merge silencieux
    cross-batch par une erreur metier listant les cles ) .
- Tests : `IntraImportDuplicateDetectorTest` ( SQL fige + OFF/null no-op +
  cas nominal sans scan sample + WARN/FAIL ) .

## 3. Race conditions identifiees

### RC-1 : Cancel vs register checkpoint Phase 2

Le cancel utilise `CancellationContext.checkpoint()` injecte dans
`DataService.addData` . Si le cancel arrive entre 2 checkpoints , le
travail entre les 2 checkpoints continue jusqu'au prochain . Maximum
exposure : taille d'un batch UPSERT .

**Mitigation existante** : SLA cancel 5s ( tache #233 ) , checkpoint
toutes les ~3-5 sec .

### RC-2 : 2 PUBLISH concurrents sur meme `binaryfile.id`

Verrou existant : `commitPublishVisibility` utilise `SELECT FOR UPDATE`
sur la row binaryfile ( P0-2 du commit consolide V4-V9 ) . OK .

### RC-3 : 2 UNPUBLISH concurrents

Meme verrou `FOR UPDATE` . OK theoriquement , mais la phase 1 ( markPending )
n'est pas verrouilles . 2 unpublish peuvent demarrer en parallele + se
bloquer mutuellement sur la phase 2 -> 1 reussit , l'autre erreur
"already unpublished" .

**Mitigation** : ajouter le verrou des Phase 1 ( tache #232 deja
identifiee ) .

**STATUS ( verifie 29-05-2026 )** : DEJA RESOLU . `startPhase1`
( `PublishLifecycleService` ) serialise toute entree concurrente sur le
meme fileId via 3 couches :
1. `pg_advisory_xact_lock(hashtext(fileId))` ( L376 ) - verrou bloquant ,
   auto-libere au COMMIT/ROLLBACK ; le 2eme unpublish attend la fin du 1er .
2. `rejectIfWorkflowAlreadyInProgress` -> `WorkflowAlreadyInProgressException`
   ( HTTP 409 ) couvrant PUBLISH / UNPUBLISH / DELETE_FILE via
   `ACTIVE_WORKFLOW_TYPES` . Le perdant recoit un 409 clair , jamais
   "already unpublished" .
3. Defense-in-depth : index UNIQUE partiel
   `workflow_log_uniq_active_per_file_idx` ( Flyway main V10 ) -> SQLSTATE
   23505 si 2 INSERT IN_PROGRESS passent malgre tout .
=> aucun changement de code requis .

### RC-4 : SessionRegistry vs SessionTerminator

`SessionInfo` registry in-memory + cleanup scheduler . Si un user logout
pendant que le scheduler purge les sessions expirees , les 2 modifient
la meme entree . Le registry utilise `ConcurrentHashMap` - les
operations individuelles sont atomic , mais le "compute + remove"
peut etre split .

**Mitigation** : utiliser `computeIfPresent` ou `compute` au lieu de
`get` puis `remove` .

**Status ( verifie 29 mai )** : **DEJA SUR** . `UserSessionRegistry` n'a
aucun pattern get+remove : `finish()` utilise `computeIfPresent` ,
`detectJwtExpired` utilise `replaceAll` , l'eviction utilise
`entrySet().removeIf` ( tous atomiques cote ConcurrentHashMap ) . Aucune
action requise .

### RC-5 : Cache invalidation cross-application

`authorizationScopesCache` ( tache #313 ) est aujourd'hui invalide
globalement par app . En cas d'invalidation pendant qu'un autre
import calcule l'autorisation , l'import voit potentiellement un
miss -> recalcul couteux .

**Mitigation** : invalidation ciblee par datatype au lieu de par app .

## 5. Design BDD - observations

### D-1 : `binaryfile.filedata` ( bytea ) + `binaryfile.processed_data` ( oid )

**Force** : separation TOAST ( bytea ) vs Large Object ( streamable 4TB ) -
explique le choix . Bytea inline limite ~1 GB ; LO pour les exports
massifs .

**Faiblesse** : 2 chemins de stockage = 2 paths de cleanup distincts .
Cf P0-2 sur les LO orphelines .

### D-2 : `oa_audit` schema separe

Bonne separation **isolation** : workflow_log peut etre archive sans
toucher aux donnees applicatives . Plus simple a sauvegarder
incrementalement .

### D-3 : `oa_staging` schema

Mode UNLOGGED pour eviter le WAL . **Risque** : crash = perte staging ,
mais staging est cense etre rebuild par Phase 2 . OK pour cette
contrainte business .

### D-4 : Postgres roles ( `<userid>_userManager` , `<userid>_applicationManager` )

Modele de permissions par role Postgres + RLS . Tres securise mais
genere beaucoup de roles ( 1 par user par app ) . Pour 1000+ users
avec 50 apps , on peut atteindre des dizaines de milliers de roles
Postgres -> degradation perf catalog .

**Mitigation** : monitoring `pg_authid` count . Si > 5000 roles ,
dans l e futur : envisager passer a RLS sans role-per-user .

### D-5 : Hikari pool unique

`SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE=80` + `STREAMING_HIKARI_MAXIMUMPOOLSIZE=30`
Total = 110 connexions Postgres ( max 150 cote PG ) . Marge ~26% .

**Risque** : si HTTP burst , le pool HTTP sature avant que le streaming
pool soit utilise -> latence HTTP+import . Tache #308 deja ouverte
sur "Pool Hikari separe cascade vs HTTP" .

## 6. Cascade architecture - observations

### C-1 : `OncePerRequestFilter HttpAccessErrorLogFilter` ( nouveau , session 29 mai )

OK SOLID DRY . Log toute reponse HTTP >= 400 en WARN/ERROR . Filtre
configurable via `openadom.access-log.min-status` + exclude prefix .

### C-2 : `WorkflowProgressReporter` + `PhaseScope`

Architecture moderne ( tache #284-#286 ) qui force le phase tracking
explicite . SRP + OCP respecte . Le seul risque est l'oubli d'un
`PhaseScope.open` dans une future methode `doFooBar` - difficilement
detectable a la compilation . Mitigation : annotation ou test
verifiant que toutes les methodes Phase2Handler.do* sont wrappees .

### C-3 : `AuthorizationFilter` JWT validation

Chaine de filtres Spring Security . Pas de cache sur la verification
JWT - chaque requete decode + verifie le token . Pour > 1000 req/s ,
cela peut etre un goulot ( crypto verify ) .

**Mitigation** : cache local JWT-id -> Authentication object pendant la
duree de validite du JWT . **Risque** : invalidation lors d'un kick
( JWT revoque ) doit etre instantanee -> cache doit etre invalide via
event .

## 10. Passage a l'echelle : staging -> table finale ( dizaines de M de lignes )

Analyse du chemin `COPY staging` -> `UPSERT final` ( `StagingFinalizeSql` ,
`StagingUpsertSqlBuilder` , `RefrefRebuildSql` , `DataRepository.storeAll` )
pour des imports de plusieurs dizaines de millions de lignes .

### Deja en place ( bon , a conserver )

- **COPY FROM STDIN** vers staging ( pas d'INSERT ligne a ligne ) - protocole
  binaire , optimal .
- **UPSERT par batch CTE `DELETE ... RETURNING` par `ctid`** ( 50 000 lignes ) :
  pas d'OFFSET ( cout constant par batch ) , consomme le staging au fur et
  a mesure .
- **Extraction colonne-par-colonne** ( P4b , `useColumnExtractionUpsert=true` )
  au lieu de `jsonb_populate_record` -> supprime le lookup syscache par
  ligne ( ~20-30 % du temps finalize sur 1M+ ) .
- **`reference_reference` rebuild incremental** ( O( lignes republiees ) , pas
  O( table entiere ) ) via JOIN sur la contrainte unique .
- **Synthese via `referencevalue_count_stats`** ( triggers statement-level ) :
  lecture PK < 1 ms au lieu d'un `COUNT(*)` ( 2-5 min sur 200M ) .
- **`SHARED_UNLOGGED` + `DIRECT_COPY`** + `synchronous_commit=off` cluster +
  `ANALYZE staging` avant UPSERT + `lock_timeout` + retry ( 55P03 / 40P01 /
  40001 ) avec SAVEPOINT par batch .

### Leviers d'amelioration ( par ordre de ROI )

| # | Levier | Detail | Gain attendu | Risque |
|---|--------|--------|--------------|--------|
| S-1 | **Index sur la cle de conflit avant tout** | l'UPSERT `ON CONFLICT ON CONSTRAINT hierarchicalKey_uniqueness` maintient l'index B-tree a chaque ligne . Sur 10M+ , l'insertion dans un index deja gros domine . **A mesurer** : si table finale initialement vide / republish massif , `DROP INDEX` non-uniques + recreate `CONCURRENTLY` apres le COPY ( garder l'unique , obligatoire pour ON CONFLICT ) . Generique : ne le faire que si EXPLAIN montre l'index maintenance comme dominant . | 2-4x sur gros republish | recreate index = fenetre sans index ; garder l'unique |
| S-2 | **Batch 50k -> 100k adaptatif** | moins d'iterations ( 100M = 1000 au lieu de 2000 ) . Trade-off : verrous tenus ~2x plus longtemps par batch . Rendre la taille **configurable + adaptative** ( reduire si lock_timeout detecte ) . | -10/20 % wall-clock | contention si publishes concurrents |
| S-3 | **Sink parallelism reel** | `DIRECT_COPY + SHARED_UNLOGGED` autorise N writers ( `CASCADE_POOL_SINK` ) . Verifier qu'on sature les coeurs DB sans depasser le pool Hikari cascade ( 30 ) . Tuner par hardware . | lineaire jusqu'a contention I/O | saturation connexions |
| S-4 | **Partitionnement de `referencevalue` par `referenceType` ( ou binaryfile )** | sur des tables de 100M+ , partitionner permet : DELETE/republish par `DROP/TRUNCATE PARTITION` ( O(1) au lieu de DELETE chunke ) , VACUUM cible , plans plus petits . **Le plus structurant** pour le tres gros volume . Approche generique ( declarative partitioning PG ) . | DELETE_FILE/UNPUBLISH O(1) + scans plus petits | migration schema lourde , a planifier |
| S-5 | **`maintenance_work_mem` / `work_mem` par session finalize** | `SET LOCAL` avant l'UPSERT pour accelerer tri/hash + creation index . | tri/hash plus rapides | RAM par connexion |
| S-6 | **Eviter le rebuild synthese complet** | `SynthesisService` fait DELETE + recompute complet de la synthese ; deja rapide via stats table mais le `Chart.toSQL` peut scanner . A verifier en EXPLAIN sur gros datatype . | variable | - |
| S-7 | **`pg_repack` pour le bloat post-republish massif** | apres de gros DELETE+INSERT , la table finale bloat ; `pg_repack` ( online ) au lieu de `VACUUM FULL` ( lock ) . Job de maintenance . | reduit bloat / taille index | extension a installer |

### Recommandation cle pour le TRES gros volume

**S-4 ( partitionnement )** est le seul changement vraiment structurant : il
transforme DELETE_FILE / UNPUBLISH d'un `DELETE` chunke O( lignes ) en un
`DROP PARTITION` O(1) , reduit la taille des index maintenus pendant
l'UPSERT , et borne le cout des scans . A planifier comme chantier dedie
( migration declarative , compat RLS a valider ) . Les autres leviers ( S-1 ,
S-2 , S-3 ) sont des reglages a activer selon ce que montre `EXPLAIN
ANALYZE` + le monitoring , sans refonte .

## 9. Conclusion

Le backend OpenADOM est globalement bien instrumente ( phase tracking ,
heartbeat , workflow_log , cancellation ) . Les invariants de coherence
sont identifies et la plupart des verrous sont en place .

**Risques residuels majeurs** :
1. P0-1 ( retention task ) - **fix applique** ✓
2. P0-2 ( LO orphelines ) - **DEJA RESOLU** ✓ ( LO #244 actif , `lo_unlink`
   atomique dans persist/clear + `LargeObjectOrphanSweeper` nightly ; 0 orphelin )
3. P0-4 ( DELETE_FILE non-atomique ) - **compensation auto-reparante B**
   ( reutiliser `CompensationLogService` ; SAVEPOINT rejete pour l'echelle )
4. P0-5 ( PUBLISH crash recovery ) - **atomicite confirmee en code** ✓ ;
   procedure de chaos test live documentee ( a derouler manuellement )
5. RC-3 ( UNPUBLISH concurrent ) - **deja resolu** ✓ ( advisory xact lock
   par fileId + reject-if-active 409 + index UNIQUE partiel V10 )
6. P1-3 ( doublons natural-key intra-import ) - **implemente** ✓
   ( detection staging , policy OFF/WARN/FAIL , defaut WARN iso-resultat )

Reponse a la question B vs C ( P0-4 ) : **B ( compensation auto-reparante )**
gagne sur perf-a-l'echelle ET coherence . C ( SAVEPOINT ) forcerait une
transaction monolithique sur des dizaines de M de lignes -> regression
( annule le decoupage chunke 10k qui est la cle du scale ) .

**Passage a l'echelle ( section 10 )** : le pipeline COPY->UPSERT est deja
solide ( COPY , batch CTE par ctid , extraction colonne P4b , refref
incremental , stats table ) . Le seul chantier structurant pour le TRES
gros volume est le **partitionnement de `referencevalue`** ( S-4 ) :
DELETE_FILE / UNPUBLISH en `DROP PARTITION` O(1) + index/scans plus petits .
Les autres leviers ( S-1 index , S-2 batch , S-3 parallelism , S-5 work_mem )
sont des reglages a activer selon `EXPLAIN ANALYZE` + monitoring .

Les optimisations P2 ( pgbouncer , cache JWT , pool Hikari separe ) ne
sont a faire que si le monitoring montre une saturation reelle .
