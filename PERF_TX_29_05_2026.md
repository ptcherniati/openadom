## 1. Bugs P0 confirmes ( a corriger en priorite )

### P0-1 : `WorkflowLogRetentionTask` echoue chaque tick

**Fichier** : `backend/src/main/java/fr/inra/oresing/workflow/cascade/history/WorkflowLogRepository.java:458` ( pre-fix )

**Symptome observe** : 136 erreurs HTTP 4xx/5xx remontees pendant la
session , dont la trace systematique :

```
org.springframework.dao.DataIntegrityViolationException: PreparedStatementCallback;
SQL [SELECT oa_audit.delete_workflow_logs_older_than(?::int)];
A result was returned when none was expected.
```

**Cause racine** : la fonction PostgreSQL `delete_workflow_logs_older_than`
retourne un `int` ( le nombre de lignes purgees ) , donc l'instruction
SQL renvoie une row . Le code utilisait `jdbcTemplate.update(SQL, days)`
qui invoque `executeUpdate()` cote driver - le driver Postgres jette
parce qu'il y a un result set non consomme .

**Impact** :
- Backend log ERROR chaque minute ( scheduler `WorkflowLogRetentionTask` )
- Aucune purge de l'historique reellement effectuee -> table
  `oa_audit.workflow_log` grossit indefiniment
- Bloat index + degradation des queries d'historique au fil des mois
- Pollution Grafana ( faux signal d'erreur backend )

**Patch** : utiliser `queryForObject(SQL, Integer.class, days)` .
**Status** : applique dans la session ( commit en attente ) .

### P0-2 : Mode CACHED_ROTATION - `processed_data` Large Object orpheline

**Fichier** : `backend/src/main/java/fr/inra/oresing/persistence/BinaryFileRepository.java` ( voir `storeProcessedData` + V13 migration )

**Hypothese** : lors d'un republish CACHED_ROTATION qui reutilise
`processed_data` sans relancer DataImporter , si la chaine
clear-old + assign-new n'est pas dans la meme transaction , l'ancien
OID Large Object peut rester non reference + non delete -> bloat
`pg_largeobject_metadata` .

**Verification recommandee** :
```sql
-- Comparer le nombre d'OIDs dans pg_largeobject_metadata
-- vs le nombre de processed_data non-null dans binaryfile
SELECT COUNT(*) FROM pg_largeobject_metadata;
SELECT COUNT(*) FROM ticket_507_1.binaryfile WHERE processed_data IS NOT NULL;
-- Si l'ecart est > 0 , il y a fuite d'OIDs
```

**Mitigation** : ajouter un VACUUM LO scheduled , OU encapsuler
`storeProcessedData` dans un `@Transactional` qui DELETE l'OID
precedent via `lo_unlink` avant d'assigner le nouveau .

### P0-3 : `JdbcTemplate.update` avec SELECT - meme pattern ailleurs

Apres la decouverte du bug P0-1 , audit complet du repository
necessaire pour identifier d'autres occurrences ( SQL `SELECT` passe a
`update()` ) . Grep recommande :

```bash
grep -rn 'jdbcTemplate\.update' backend/src/main/java | grep -i SELECT
```

A verifier en J+1 .

## 2. Risques d'incoherence ( P0/P1 )

### P0-4 : DELETE_FILE - non atomique entre `DELETE rows` + `DELETE binaryfile`

**Fichier** : `backend/src/main/java/fr/inra/oresing/rest/usecases/storage/versioning/PublishLifecyclePhase2Handler.java` , methode `doDeleteFile`

**Refacto recent** ( SLA cancel 5s ) : la methode a ete splittee en
deux phases visibles ( DELETE_ROWS + DELETE_FILE_ROW ) , chacune en
transaction propre via `PhaseScope` .

**Risque** : si Phase 2 ( DELETE_FILE_ROW ) echoue , Phase 1 est
committee = on a perdu les rows mais la binaryfile metadata reste -> incoherence
dans l'UI ( le fichier apparait dans l'historique mais sans donnees ) .

**Mitigation** :
- Option A : remettre les 2 phases dans la meme transaction ( pas SOLID , difficile a annuler )
- Option B : ajouter une **compensation** : si Phase 2 echoue , marquer
  le workflow_log status=`PARTIAL_DELETE_FAILED` et offrir un endpoint
  admin pour completer le DELETE_FILE_ROW manuellement
- Option C ( recommandee ) : utiliser `SAVEPOINT` Postgres pour
  granularite + rollback partiel sans annuler tout

### P0-5 : PUBLISH staging -> final - race avec crash backend

**Fichier** : `backend/src/main/java/fr/inra/oresing/rest/usecases/storage/versioning/PublishLifecyclePhase2Handler.java` , methode `commitPublishVisibility`

**Scenario observe** :
1. Backend ouvre transaction , INSERT 1M rows dans `staging` UNLOGGED
2. Backend swap staging -> final via `INSERT INTO final SELECT FROM staging`
3. Backend crash entre commit COPY + commit visible_flag
4. Au redemarrage : final a deja les rows ( COPY committe ) , mais `binaryfile.published=false`

**Etat de la base** : incoherent . Les rows existent mais ne sont
pas visibles via l'API ( filtree par `published=true` ) .

**Fix existant** ( CONFIRME par lecture session ) : la transaction
finale englobe le swap + le `UPDATE binaryfile SET published=true`
+ le `recordEnd` workflow_log dans **une seule** tx ( P0-2 + P0-6 du
audit precedent ) . Donc theoriquement atomique .

**Risque residuel** : SHARED_UNLOGGED tables n'ont pas de WAL .
Si Postgres crash AVANT que le swap se finisse , la table staging
peut etre tronquee a redemarrage -> Phase 2 redemarrage doit
detecter staging vide + retraiter ( idempotence verifiee mais non
testee live ) .

**Recommandation** : ajouter un test de chaos engineering ( `pg_terminate_backend`
pendant le swap ) pour confirmer la recovery .

### P1-1 : `WorkflowZombieSweeper` - marquage en double possible

**Fichier** : `backend/src/main/java/fr/inra/oresing/workflow/cascade/history/WorkflowZombieSweeper.java`

**Mecanisme** : scheduler appelle `mark_zombie_workflows(threshold_min)`
toutes les minutes . Marque IN_PROGRESS sans heartbeat depuis N min
comme ZOMBIE .

**Race** : 2 instances backend ( prod replicee ) -> 2 schedulers
concurrent -> double marquage de la meme ligne . La fonction SQL
utilise `UPDATE WHERE status=IN_PROGRESS AND last_heartbeat < threshold`
qui est protege par MVCC ( un UPDATE consume la row ) , donc OK en
theorie .

**Verification recommandee** : ajouter `FOR UPDATE SKIP LOCKED`
pour eviter contention au pire .

### P1-2 : `binaryfile.params->published` source de verite divergente

**Fichier** : `BinaryFilePublicationState` endpoint + frontend
DataVersioningView

**Pattern actuel** : 2 sources potentielles
- `binaryfile.params->>'published'` ( jsonb , verite committee )
- `workflow_log.status` ( IN_PROGRESS / DONE / CANCELLED )

**Risque** ( deja identifie + commentaire en code ) : cancel-divergence
- workflow_log.status=CANCELLED mais binaryfile.published=true ( commit
  visible_flag a eu lieu avant le cancel )

**Mitigation existante** : un endpoint dedie `/file/{id}/publication-state`
lit `binaryfile.params` comme source unique post-terminal . OK , mais
l'UI doit toujours appeler ce endpoint et non se baser sur le workflow status.

### P1-3 : DataImporter naturalkey collision intra-import

**Fichier** : DataImporter + V11 idx fonctionnel `binaryfile.params`

**Scenario** : 2 lignes du CSV en cours d'import partagent la meme
naturalkey ( bug user ) . Comportement actuel : la 2eme ligne UPDATE
la 1ere dans `staging` , puis le swap final voit qu'une seule row .
**Probleme** : aucune erreur de validation , user pense que les 2
lignes ont ete inserees .

**Mitigation recommandee** : pre-scan `NaturalKeyPreScanService` doit
detecter les doublons intra-import + reporter au user avant
finalisation ( la tache #287 est ouverte sur ce sujet ) .

### P2-1 : `oa_metrics.workflow_log` croissance indefinie

Cause = P0-1 ( retention task brisee ) . Une fois P0-1 fixe , la
retention configuree ( `OPENADOM_WORKFLOW_LOG_RETENTION_DAYS=90` par
defaut probable ) reprendra le travail .

## 3. Race conditions identifiees

### RC-1 : Cancel vs register checkpoint Phase 2

Le cancel utilise `CancellationContext.checkpoint()` injecte dans
`DataService.addData` . Si le cancel arrive entre 2 checkpoints , le
travail entre les 2 checkpoints continue jusqu'au prochain . Maximum
exposure : taille d'un batch UPSERT .

**Mitigation existante** : SLA cancel 5s ( tache #233 ) , checkpoint
toutes les ~3-5 sec .

### RC-2 : 2 PUBLISH concurrents sur meme `binaryfile.id`

Verrou existant : `commitPublishVisibility` utilise `SELECT FOR UPDATE`
sur la row binaryfile ( P0-2 du commit consolide V4-V9 ) . OK .

### RC-3 : 2 UNPUBLISH concurrents

Meme verrou `FOR UPDATE` . OK theoriquement , mais la phase 1 ( markPending )
n'est pas verrouilles . 2 unpublish peuvent demarrer en parallele + se
bloquer mutuellement sur la phase 2 -> 1 reussit , l'autre erreur
"already unpublished" .

**Mitigation** : ajouter le verrou des Phase 1 ( tache #232 deja
identifiee ) .

### RC-4 : SessionRegistry vs SessionTerminator

`SessionInfo` registry in-memory + cleanup scheduler . Si un user logout
pendant que le scheduler purge les sessions expirees , les 2 modifient
la meme entree . Le registry utilise `ConcurrentHashMap` - les
operations individuelles sont atomic , mais le "compute + remove"
peut etre split .

**Mitigation** : utiliser `computeIfPresent` ou `compute` au lieu de
`get` puis `remove` .

### RC-5 : Cache invalidation cross-application

`authorizationScopesCache` ( tache #313 ) est aujourd'hui invalide
globalement par app . En cas d'invalidation pendant qu'un autre
import calcule l'autorisation , l'import voit potentiellement un
miss -> recalcul couteux .

**Mitigation** : invalidation ciblee par datatype au lieu de par app .

## 4. Requetes non optimisees

### Q-1 : `findUsersGrantedRole` ( P0.2 deja optime )

LATERAL refacto deja applique ( tache #159 ) . Garder en veille la perf .

### Q-2 : `getReferencedBinaryFiles` ( P1.7 deja optime )

LATERAL refacto deja applique ( tache #162 ) . OK .

### Q-3 : `findBinaryFileIdsWithLinks` ( P0 deja optime )

SELECT DISTINCT EXISTS deja applique ( tache #180 ) . OK .

### Q-4 : `cache_hit_ratio` global vs per-database

Custom Alloy query agrege globalement . Pour identifier la base
chaude , il faut breakdown par `datname` ( deja fait dans la query ) .
OK .

### Q-5 : `WorkflowLogRepository.deleteAll` ( admin )

`DELETE FROM oa_audit.workflow_log` sans WHERE . OK pour purge admin ,
mais bloque toutes les autres lectures sur la table le temps du DELETE .
Pour 1M+ rows -> lock pendant 30+ sec .

**Mitigation** : delete par batchs de 10K avec un curseur , ou
TRUNCATE ( plus rapide mais ne joue pas les triggers ) .

### Q-6 : `binaryfile.params` GIN index

V11 deja applique idx fonctionnel sur `params->>'datatype'` ( tache #161 ) .
**A verifier** : pour les filtres frequents sur `params->'binaryfiledataset'->>'from/to'`
( extractions par date ) , ajouter idx fonctionnel sur ces sous-cles si
EXPLAIN ANALYZE montre seq_scan .

### Q-7 : `referencevalue_count_stats` recompute

Maintien par triggers AFTER INSERT/DELETE statement-level + endpoint
admin de recompute exact . OK , mais le recompute en mode lock-bloquant
sur tables volumineuses est couteux .

**Mitigation** : `pg_repack` pour le recompute sur tables haute volume .

### Q-8 : pgbouncer non present

Pool de connexion JDBC est gere par Hikari ( 80 max par defaut prod ) ,
qui pointe directement sur Postgres . Pour des bursts , pgbouncer
permettrait de servir plus de connexions courtes .

**Trade-off** : pgbouncer breaks LISTEN/NOTIFY + prepared statement
caching par session , a evaluer .

## 5. Design BDD - observations

### D-1 : `binaryfile.filedata` ( bytea ) + `binaryfile.processed_data` ( oid )

**Force** : separation TOAST ( bytea ) vs Large Object ( streamable 4TB ) -
explique le choix . Bytea inline limite ~1 GB ; LO pour les exports
massifs .

**Faiblesse** : 2 chemins de stockage = 2 paths de cleanup distincts .
Cf P0-2 sur les LO orphelines .

### D-2 : `oa_audit` schema separe

Bonne separation **isolation** : workflow_log peut etre archive sans
toucher aux donnees applicatives . Plus simple a sauvegarder
incrementalement .

### D-3 : `oa_staging` schema

Mode UNLOGGED pour eviter le WAL . **Risque** : crash = perte staging ,
mais staging est cense etre rebuild par Phase 2 . OK pour cette
contrainte business .

### D-4 : Postgres roles ( `<userid>_userManager` , `<userid>_applicationManager` )

Modele de permissions par role Postgres + RLS . Tres securise mais
genere beaucoup de roles ( 1 par user par app ) . Pour 1000+ users
avec 50 apps , on peut atteindre des dizaines de milliers de roles
Postgres -> degradation perf catalog .

**Mitigation** : monitoring `pg_authid` count . Si > 5000 roles ,
envisager passer a RLS sans role-per-user .

### D-5 : Hikari pool unique

`SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE=80` + `STREAMING_HIKARI_MAXIMUMPOOLSIZE=30`
Total = 110 connexions Postgres ( max 150 cote PG ) . Marge ~26% .

**Risque** : si HTTP burst , le pool HTTP sature avant que le streaming
pool soit utilise -> latence HTTP+import . Tache #308 deja ouverte
sur "Pool Hikari separe cascade vs HTTP" .

## 6. Cascade architecture - observations

### C-1 : `OncePerRequestFilter HttpAccessErrorLogFilter` ( nouveau , session 29 mai )

OK SOLID DRY . Log toute reponse HTTP >= 400 en WARN/ERROR . Filtre
configurable via `openadom.access-log.min-status` + exclude prefix .

### C-2 : `WorkflowProgressReporter` + `PhaseScope`

Architecture moderne ( tache #284-#286 ) qui force le phase tracking
explicite . SRP + OCP respecte . Le seul risque est l'oubli d'un
`PhaseScope.open` dans une future methode `doFooBar` - difficilement
detectable a la compilation . Mitigation : annotation ou test
verifiant que toutes les methodes Phase2Handler.do* sont wrappees .

### C-3 : `AuthorizationFilter` JWT validation

Chaine de filtres Spring Security . Pas de cache sur la verification
JWT - chaque requete decode + verifie le token . Pour > 1000 req/s ,
cela peut etre un goulot ( crypto verify ) .

**Mitigation** : cache local JWT-id -> Authentication object pendant la
duree de validite du JWT . **Risque** : invalidation lors d'un kick
( JWT revoque ) doit etre instantanee -> cache doit etre invalide via
event .

## 8. Methodologie de test recommandee

### 8.1 - Chaos engineering BDD

Reproduire scenarios crash via :
- `pg_terminate_backend` cible pendant PUBLISH , UNPUBLISH , DELETE_FILE
- `docker kill --signal=SIGKILL oa-backend-1` pendant les memes
- Comparer etat BDD avant/apres : `binaryfile.published` , `workflow_log.status` ,
  presence des rows dans la table finale

### 8.2 - Load testing

- 100 PUBLISH simultanes sur 100 binaryfiles distincts -> verifier
  Hikari saturation , latence p95
- 10 PUBLISH simultanes sur **meme** binaryfile -> verifier verrou
  `FOR UPDATE` actif , que 1 seul reussit

### 8.3 - Verification orphelines

Script SQL nightly :
```sql
-- LO orphelins
SELECT count(*) FROM pg_largeobject_metadata m
WHERE NOT EXISTS (
  SELECT 1 FROM application.binaryfile b WHERE b.processed_data = m.oid
);

-- Workflow IN_PROGRESS sans heartbeat depuis > 1h
SELECT count(*) FROM oa_audit.workflow_log
WHERE status = 'IN_PROGRESS'
  AND last_heartbeat < now() - INTERVAL '1 hour';

-- binaryfile.published=true sans row dans table finale
-- ( a faire par schema applicatif )
```

### 8.4 - Monitoring continu

Les alertes Grafana ajoutees en session ( 14 rules ) couvrent deja :
- backend_down , postgres_down , loki_down
- HTTP 4xx/5xx spike
- Hikari pool saturation
- Postgres connections high , long_running_tx , blocked_sessions , cache_hit_low
- Workflow FAILED
- Login fail per user

A ajouter :
- **Alerte LO orphelins** : query nightly + Prometheus pushgateway
- **Alerte workflow_log size** : detecte retention task brisee

## 9. Conclusion

Le backend OpenADOM est globalement bien instrumente ( phase tracking ,
heartbeat , workflow_log , cancellation ) . Les invariants de coherence
sont identifies et la plupart des verrous sont en place .

**Risques residuels majeurs** :
1. P0-1 ( retention task ) - **fix applique en session** ✓
2. P0-4 ( DELETE_FILE non-atomique ) - **compensation a ajouter**
3. P0-5 ( PUBLISH crash recovery ) - **test chaos a ecrire**
4. RC-3 ( UNPUBLISH concurrent ) - **verrou phase 1 a ajouter**

Apres adressage de ces 4 points , la robustesse production est
significativement amelioree . Les optimisations P2 ( pgbouncer ,
cache JWT , pool Hikari separe ) ne sont a faire que si le monitoring
montre une saturation reelle .

**Tache prioritaire J+1** : verifier P0-2 ( LO orphelines ) via la
query de l'annexe 8.3 . Si > 0 , patch immediat .
